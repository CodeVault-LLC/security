# Report model

One source of truth, three publication views. The internal report, the vendor
report and the public advisory are projections of the same research case, not
three documents that have to be kept in sync by hand.

## Why projections

A researcher who maintains three separate documents ends up with three versions
of the affected-version list, and one of them is wrong when the vendor asks. In
CodeVault the facts live once — on the finding, the asset, the scores, the
evidence, the disclosure timeline — and each report is a view of the subset its
audience may see.

## The visibility rule

```
INTERNAL report  may consume  INTERNAL, VENDOR, PUBLIC
VENDOR   report  may consume            VENDOR, PUBLIC
PUBLIC   report  may consume                    PUBLIC
```

One function, `canInclude`, in `packages/core/src/visibility.ts`. It is applied:

1. when the AI context for a report action is built;
2. when a directive is resolved during rendering;
3. when the linter runs before approval;
4. when the linter runs again in the worker, immediately before the PDF is
   produced.

Four times, deliberately. This is the property the product exists to guarantee,
and a single checkpoint is a single point of failure.

Promotion — moving an item from INTERNAL to VENDOR, or VENDOR to PUBLIC — is
always an explicit human action, and it is audited separately from ordinary
edits.

## Templates

Three built-in templates in `packages/reporting/src/templates/`. Each defines an
audience, a default TLP marking, a visibility ceiling, an ordered section list,
which sections are required, and a purpose statement per section.

That purpose statement appears above the editor *and* is what an AI drafting
action is told to write toward, so the researcher and the model are working from
the same brief.

| Template | Audience | Default TLP | Shape |
| --- | --- | --- | --- |
| `CODEVAULT_INTERNAL_V1` | INTERNAL | TLP:RED | Full research record, including failed hypotheses and disclosure strategy |
| `CODEVAULT_VENDOR_V1` | VENDOR | TLP:AMBER | What the vendor needs to reproduce and fix it |
| `CODEVAULT_PUBLIC_V1` | PUBLIC | TLP:CLEAR | What users need to protect themselves |

The internal template includes a section for alternative exploitation and failed
hypotheses. It is the section future researchers actually need and the one no
other format has room for.

## Directives

Markdown is canonical. Structured data enters it through directives:

```markdown
[evidence:EVID-000123]
[asset:AST-000012]
[finding:FIND-2026-0012]
[reference:REF-00042]
[score:CVSS40]
[disclosure-timeline]
```

Each resolves through the database at render time and carries the real
visibility of the record it points at. Three consequences:

- A figure cannot go stale, because it is not a copy.
- A directive the audience may not see is **refused**, and renders as a visible
  error marker — never silently dropped, and never printing the identifier of
  the internal record it referenced.
- An unknown directive is an error too. A report with a hole where a figure
  should be is worse than one that says so.

## Rendering

```
Approved Markdown
  → resolve directives (visibility-checked, per audience)
  → Remark AST                     (raw HTML dropped here, not sanitised later)
  → Rehype AST
  → sanitise against an allow-list (no script, no iframe, no SVG, no remote images)
  → substitute directive HTML      (trusted, generated by us, after sanitisation)
  → CodeVault report template
  → Paged.js pagination            (running TLP header, page counters)
  → Chromium, networking disabled
  → tagged PDF with an outline
  → SHA-256
  → object storage + report_exports row
```

Report Markdown quotes payloads taken from research targets, so it is untrusted
input. Raw HTML is dropped at the AST boundary rather than sanitised afterwards,
and link protocols are limited to `http`, `https` and `mailto`.

The renderer is offline. A report that could fetch a remote image would be a way
to learn that an embargoed document had been opened, and by whom.

## The linter

`packages/reporting/src/lint.ts`. Four severities; only `BLOCKING` stops
approval and export.

**Blocking**: a required section missing or empty; an unknown, unresolved or
argument-less directive; a visibility violation; a proof of concept not approved
for the audience; a TLP marking that contradicts the audience; TLP:RED or
TLP:AMBER content quoted into a public report; an unreviewed AI draft in a
public report; a credential in a public report.

**Error**: a credential anywhere else; a private address or internal hostname in
a public report; a section whose source facts changed since approval; severity
discussed with no approved vector; a vector with no computed score.

**Warning / info**: an internal-looking filename; a CVE in the text that no
finding records; a vendor statement phrased as though CodeVault verified it.

Credential detection is deliberately noisy: a false positive costs ten seconds,
and a false negative can end an embargo.

## Approval

Sections are approved individually, recording who, when, and against which
revision. Editing an approved section drops it back to `RESEARCHER_EDITED` —
approval is of specific words, not of a section in the abstract.

Approving the whole report requires every required section approved and no
blocking lint findings. Policy packs may additionally require the approver to
differ from the last editor; the Critical Zero-Day and Program packs do.

## Export

An export is an immutable artifact: hashed, keyed opaquely, stored like any
other file, and recorded with the template version and the lint result at the
time it was produced. An advisory that was sent can be proved identical to the
one on disk.

The linter runs once more inside the worker, immediately before rendering,
because content can change between approval and export — and the export is the
thing that leaves the building.
